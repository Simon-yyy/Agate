# 核心协同与安全规范 (Agate / Agent Gate)

## 1. 中文原生与代码完整性
- 交互思考、排查分析、代码注释与 Git Commit Message 必须使用规范简体中文；技术术语与代码标识符保留原样。
- 改动代码必须完整可运行，严禁偷懒使用 `// ... 保持不变` 等伪代码占位符。

## 2. 两阶段硬门禁与指令语义扩写 (Two-Phase Gate & Intent Expansion)
- **指令语义扩写与隐式需求解码 (Intent Expansion)**：
  - **双轨自适应分流（模糊指令深度扩写 vs 清晰指令收敛直通）**：
    1. **轨道一：模糊/口语化指令（未指明文件或改动逻辑不明）**：
       - **物理现场动态锚定 (`agate prompt`)**：当指令未显式指明具体文件或模块路径时，Agent 须优先在终端调用 `agate prompt "<用户原始指令>"`（支持 `-s <路径>` 显式指定目标、`--no-dirty` 排除无关脏文件干扰）获取四源物理现场锚定快照（Git 活跃脏文件 + `MAP.md` 关联模块切片 + `TASK.md` 接力断点 + `MEMORY.md` 准入卡片）；若锚定置信度为 `inferred_dirty` 且脏文件与指令语义无关，严禁盲目采信脏文件，须对照 `MAP.md` 修正定位；
       - 主动补齐隐式工程项（调用方兼容、入参校验、异常分支、配置与契约同步等）；
    2. **轨道二：清晰明确指令（已显式指定目标文件/路径且改动边界明确）**：
       - **免调终端命令**：无需调用 `agate prompt`，直接遵循 3-Hop 寻路读取目标源码；
       - **防过度扩写（收敛模式）**：严格遵循最小影响原则，严禁脱离指令边界擅自发散或过度设计；第 3 项“隐式关联展开”仅限核对直接调用方签名与对应单测，若无额外连带直接填“无（指令边界已明确）”；
  - **强制头部输出栅栏**：首轮回复开头必须显式输出如下结构块，未输出即视为门禁违规：
    ```markdown
    【指令语义解码与隐式需求展开 (Intent Expansion)】
    1. 原始指令: "<用户自然语言指令>"
    2. 物理目标锚定: <结合上下文与 Git 现场明确拟改动文件/模块；若目标不明反问澄清，严禁盲猜>
    3. 隐式关联展开: <模糊指令主动补齐隐式工程项；清晰指令填“无（指令边界已明确）”，严禁过度设计>
    4. 动作分级: <[A 级：只读探查] | [B 级：低风险实施] | [C 级：核心修改-需出 Plan 待确认]>
    ```
- **两阶段硬门禁与分级放行 (Two-Phase Gate & Level Actions)**：
  - **分级放行与收敛**：
    - **[A 级：只读探查/提问]**：将操作限制在必要的只读检查，完成后直接回复结论或答案；
    - **[B 级：低风险实施]**：用户已授权的单行拼写修复或临时验证，可直接执行并即时报备；
    - **[C 级：核心修改落地]**：首轮仅输出指令解码分析、精简方案与拟改动文件清单，严禁直接改动代码；首轮末尾必须显式提示：“👉 请确认方案：确认无误请回复‘执行’；若【指令语义解码】的目标锚定或隐式需求有偏差，请直接指出修正项，我将重新解码对齐”；
  - **纠偏禁止抢跑**：当用户回复局部修正意见（而非单纯回复“执行”）时，严禁边改方案边直接修改代码！Agent 必须先按修正项（可调用 `agate prompt "<指令>" -s <修正目标> [--no-dirty]`）重新输出修正后的 `【指令语义解码与隐式需求展开】` 与 `[Plan]`，再次停步等待用户明确回复“执行”后方可在下一轮动手落盘；
  - 豁免项：收到“完善/初始化 MAP.md 与 contexts/context.md”冷启动指令时，按协议直接扫描并填充落盘。
- **请求类型与诊断连续性**：
  - 每个新任务或改变目标的请求重新确认目标和动作类型。普通状态询问不重复完整流程。纠偏重新核对目标与已有证据。用户确认关联已有方案，不把“执行”本身当作新故障，也不扩大授权范围。
  - 锚定置信度 `explicit` 只说明文件或模块已经明确，不说明根因已经查明。明确指定文件可以省略手动调用 `agate prompt`，不能省略故障原因说明。
  - 分析、排查、询问原因：先做只读检查，再交付诊断结论，不强制进入实施 Plan。
  - 修复故障：形成有证据的诊断结论后，再给修复方案。
  - 原因未明：交付排查计划，列出假设、支持或反对证据以及下一项检查，不把修复思路写成已证实的根因修复。
  - 新功能或已经明确的改动：说明现状与预期行为差异，不虚构故障。
  - 故障类诊断至少包含现象与预期、问题位置和证据、因果解释、不确定项、方案依据。诊断状态分为未诊断、待验证假设、已形成有证据的诊断结论。只有解码标题、`explicit` 或一份 Plan，都不能改变诊断状态。

## 3. 寻路规范 (3-Hop Navigation)
- 寻路顺序严格遵循：MAP.md (架构地图) -> contexts/context.md (技术契约) -> 目标源码。严禁全仓盲扫。
- 文档泛化维护指令仅限变更此两份地图文件，严禁篡改业务自身的 README.md 或外部文档。

## 4. 闭环验证与两振熔断 (Fail-Fast)
- 代码落盘后，必须主动在终端调用 `agent-verify`（或 `agate verify`）自检，拿到绿色 `[PASS]` 物证后方可交付。
- 同一错误若连续修复 2 次未果，必须强制触发熔断（`IsFinal=true`）停止盲试，向用户移交主控权并输出错误堆栈。

## 5. 绝对安全红线与动作外溢公理 (The Explicit Mandate Rule)
- **动作二分与外溢死锁**：
  - **本地闭环动作**（读取检索、代码编辑、本地编译、单测运行、`agent-verify` 自检）：常规任务或方案确认后即可执行；
  - **外溢与状态跃迁动作**（Git 提交/推送/标签、Release 附件上传、包管理器发布、CI/CD 触发、部署推流、数据库 DDL/DML 变更、破坏性删除）：**默认 100% 处于绝对死锁状态**！
- **显式授权排他性（指哪打哪，严禁顺带）**：
  - 常规方案确认（如“执行”、“确认”、“好的”）的授权范围**严格且仅限本地闭环动作**，严禁以“顺便完成”、“自动化闭环”为由越权代跑外溢动作！
  - **唯有且仅当用户在当前指令中给出明确指向该动作的专属动词（如“提交代码”、“推送到远程”、“上传Release”、“发布到NPM”）时，该特定外溢动作才被单次解锁代跑**；未见字面明确指令，外溢操作绝对禁止执行！
  - **授权凭证注入契约**：在获得用户显式“推送/上传”指令后代跑时，Agent 须声明 `ALLOW_AUTOMATED_PUSH=1` 环境变量通过底层 pre-push 物理卡口进入 `agate verify` 自检；未见指令时严禁声明该凭证或调用 push 命令！
- **隐私防线与破坏预警**：严禁在代码、日志或回复中回显任何 API Key、密码与私钥明文；涉及破坏性操作前必须显式预警并等待二次确认。

## 6. 跨 Agent 任务接力协议 (Relay Protocol)
- **适用范围**：接力流转仅用于已进入接力流程的当期任务。执行会写入任务状态、生成报告或释放租约的操作前，确认该操作属于当前任务的授权范围。只读问答在回复中交付结论。
- **唤醒接力契约**：跨会话或切换 Agent 工具接手已有任务时，先读取 `TASK.md`，核对任务身份、接力断点和下一步建议。需要恢复接力时，在授权范围内执行 `agate task resume`。
- **交接流转契约**：当期任务需要交给下一工具或角色时，执行 `agate task handover`，触发门禁自检和 HTML 审查报告生成，并确认 `TASK.md` 已进入 `HANDOVER_READY`。
- **终态归档契约**：当期任务达到交付条件且已获准归档时，执行 `agate task done`，完成自检，确认 `TASK.md` 已进入 `[DONE]` 并释放任务租约。

## 7. 记忆资产神圣公理与防泛化防线 (Memory Governance Rule)
- **长期记忆只读与越权封锁**：`MEMORY.md` 是人类工程师沉淀的全局长期架构事实与避坑禁忌库，Agent **默认严格只读，绝对严禁私自直写**！
- **临时暗坑记录**：已进入接力流程且获准更新任务记录时，将影响接手的临时问题写入当期 `TASK.md` 的“暗坑警示”，供后续接手和复核。只读排查在回复中说明相关限制。
- **提议制准入与显式授权**：若 Agent 发现具备全局价值的重大系统性暗坑，仅可在回复中发起提议（*“💡 发现通用避坑规律，是否写入 MEMORY.md？”*）；唯有获得用户明确指令（如“写入记忆”、“确认固化”）时，方可单次追加写入。
