# Windows 宿主识别、指令扩写与诊断流程实施方案

日期：2026-11-13  
状态：待评审、待实施  
项目：HarnessGate / Agate

修订说明：在 Windows 宿主识别方案中，同步纳入“扩写偶尔未触发”和“解码后跳过诊断直接输出 Plan”两项问题。三个工作包分别实施、分别验收，不能以其中一项通过代替全部完成。

边界：修复对象是 Windows 本地宿主识别、请求扩写触发与诊断连续性。Cursor 是这些问题被观察到的环境，不是唯一修复对象。采集与 Editor 匹配按已确认的本地可执行文件特征实现；本次能在本机复现和验收的编辑器是 Cursor。扩写与诊断流程不绑定某一种编辑器。原生事件适配只写入已核对协议的宿主，当前有协议依据的是 Cursor Hooks；其他宿主继续使用现有 `agate prompt --hook`。

> 执行约定：获得用户明确实施授权后，使用 `superpowers:executing-plans` 按任务逐项实施。本文件记录方案，不构成修改代码、安装程序或发布的授权。

**目标**：补齐 Windows 原生祖先进程采集、每次请求的扩写触发与交付记录，以及故障诊断进入修复方案的条件，使已确认的 Windows 本地编辑器能被识别为 Editor，并减少扩写漏调和诊断跳步。Cursor 是本次观察到这些问题的环境。

**架构**：宿主识别沿用 `ProcessInspector` 和 `DetectionContext`；扩写通过宿主事件适配、请求关联及交付记录降低对模型自行调用命令的依赖；诊断以现象、证据、原因和不确定项作为修复方案的前置内容。三层之间显式传递状态，不把识别到 Editor、编译出信封或输出解码标题等同于诊断完成。

**技术栈**：Go 1.21、标准库 `syscall`、Windows Unicode API、Cobra；本次已核对的宿主事件协议是 Cursor Rules 与 Hooks。保持 `CGO_ENABLED=0`，不增加第三方依赖。

**设计依据**：本文第 1 至第 5 节规定平台识别，第 11 节规定扩写与诊断流程；第 6 至第 8 节及第 11.6 节规定实施任务、验证和验收。

## 1. 问题现场与已确认事实

### 1.1 Windows 宿主未识别

用户在 Windows 的 Cursor 集成终端中运行 `agate init`，收到未识别当前 Agent 的错误。随后在同一终端运行 `agate detect --explain`，结果为：

```text
执行者 (Runner):       未知 (unknown)
宿主编辑器 (Editor):   未知 (unknown)
传输环境 (Transports): local
首选装配目标:         无 (需显式选择 --targets)
是否存在冲突:         false
探测证据:             无
候选工具:             无
```

源码核对结果：

- `cmd/init.go` 仍然调用环境检测，自动识别功能没有被取消。
- `pkg/agent/collector.go` 的默认祖先进程采集仅实现了 Linux，非 Linux 平台直接返回空结果。
- 现有路径白名单覆盖 `.cursor-server`、`.vscode-server` 等远程服务端目录，没有覆盖本地 Windows 宿主进程。
- `pkg/agent/registry.go` 目前传入的进程采集深度为 4。
- `init` 先调用 `InspectContext`，随后又调用 `DetectEnvironmentWithProfiles`，会重复采集现场。

这些事实可以解释本次漏识别。诊断输出没有列出未命中变量的原始值，因此不能据此认定 `TERM_PROGRAM` 的具体取值。

手动输入命令时，Runner 未知可以接受。平台识别工作包要修复的是 Editor 未知，并保证不会把宿主编辑器自动升级为任务执行者。

漏识别来自 Windows 本地祖先进程未被采集，以及白名单只覆盖远程服务端目录。Cursor 集成终端是本次复现现场；同一缺口也作用于其他尚未进入匹配表的本地编辑器。

### 1.2 指令扩写未触发

用户进一步确认的表现为：某些请求没有显示指令解码，也没有调用 `agate prompt`。

检查发现：

- 项目实际规则包含要求模型调用 `agate prompt` 的文字，但调用仍取决于模型读取规则、判断条件并执行命令。
- 检查当时未发现项目级、用户级和本机系统级的 Cursor `hooks.json`；这不证明团队或插件层绝无其他 Hook。
- `agate hook` 现阶段只安装 Git 的 pre-commit、pre-push 门禁，不监听用户向模型提交请求的事件。
- `agate prompt --hook` 支持从标准输入读取文本或 JSON 载荷，输出仍为执行信封文本；它没有自动注册 Cursor 事件，也不等于已按 Cursor 原生协议投递上下文。
- 规则中的“首轮”未清楚区分新任务、普通追问和纠偏；实际项目入口与仓库当前模板也存在版本差异。

这些事实说明触发和交付链路有缺口，缺口在规则与命令链路，不限于 Cursor。本次是在 Cursor 里观察到漏触发。没有失败会话的实际上下文和事件记录，不能断言某次漏调一定由规则未加载、模型省略或其他单一原因造成。

### 1.3 解码后跳过诊断直接输出 Plan

用户报告：有时完成指令二次拆解后直接输出 Plan，没有解释问题位置、出错原因和中间证据。

检查发现：

- 项目入口及当前全局规约仍含旧要求：“遇到任何排查、探查、修复或业务修改任务，首轮仅输出指令解码分析、精简方案与拟改动文件清单”。该要求将只读排查也推向方案输出。
- 执行信封要求原始指令、目标锚定、隐式关联和动作分级，没有把现象、证据、原因及不确定项规定为修复方案的前置内容。
- `explicit` 只说明文件或模块定位明确，不说明根因已经查明。
- `agate prompt` 主要采集现场、组织提示词；命令成功和解码格式完整都不能证明已完成故障诊断。

因此需要分别解决“流程是否启动”和“启动后是否完成诊断”。这两项约束对所有宿主相同。Windows 宿主识别成功不能替代这两项验收。

## 2. 范围与约束

本次交付范围：

- Windows 通用祖先进程采集能力，不绑定某一种编辑器。
- 按已确认的本地可执行文件识别 Editor。本次实机验收在 Cursor 中进行，因为问题在该环境复现；验收结论是当前 Windows 祖先链上的编辑器被识别，不把支持范围写成只有 Cursor。
- VS Code、VS Code Insiders 作为另一种已确认的本地宿主做正例识别，并验证不会把它们装配成其他工具的规则。
- 自动检测与初始化命令的集成、测试隔离及诊断输出。
- 请求扩写的触发、关联、交付记录及失败降级。原生事件适配先落地已核对的 Cursor Hooks；接口保留宿主参数，不把扩写需求写成 Cursor 专有。
- 解码、诊断、修复方案和实施授权之间的流程约束，包含纯分析请求与原因未明时的分支。该约束与编辑器品牌无关。
- 规则来源、版本与实际加载状态的核对，防止旧全局规约继续覆盖新模板。
- 更新 `MAP.md` 与 `contexts/context.md` 中与本次变更直接相关的说明。

尚未取得实际可执行文件特征的编辑器只复用采集层，不进入匹配表，也不能宣称已支持。不得仅凭进程名猜测后补规则。已登记但本轮没有 Windows 可执行文件实据的身份包括 `codex`、`antigravity`、`claude`、`windsurf`。

全局约束：

- 保持 Go 1.21 与无 CGO 构建，不修改 `go.mod`、`go.sum` 或 vendor 依赖。
- Windows 原生采集和扩写事件适配不依赖 PowerShell、WMI、CIM、WMIC 或额外运行时；由当前宿主进程调用 Agate 二进制完成事件处理。
- 以普通权限尝试查询；访问被拒绝时降级，不请求提权。
- 不读取完整命令行、其他进程环境块或进程内存。
- 仅查询当前进程链上节点的可执行文件路径及创建时间；不把无关运行进程作为宿主证据。
- Windows 默认检查最多 8 个进程节点，包含当前进程；硬上限为 8。Linux 保持原有默认深度 4。
- 不通过修改全局环境变量或编辑器设置制造识别信号。
- 本地进程证据只作用于 Editor，不增加 Runner 判定规则。
- 检测失败仍允许用户显式指定 `-t <工具>`；冲突时继续要求显式选择。
- SSH、WSL、容器等场景保留既有检测方式，不承诺从远端进程反查本机 Windows 宿主。
- 不增加第二套模型服务或外部 LLM API；语义拆解和原因分析仍由宿主模型负责。
- 保留原有 `agate prompt`、`--hook`、`--json` 用法；宿主原生协议通过显式适配参数启用，不静默改变旧输出。
- 请求回执和诊断状态不是用户授权；不能因流程记录完整就自动取得修改、提交、推送或安装权限。
- 必须区分编译完成、上下文已交付、诊断已输出和内容已核验，禁止用同一个成功标志替代。

## 4. 采集与匹配设计

### 4.1 平台实现与接口

保留现有接口：

```go
type ProcessInspector interface {
    GetAncestors(pid int, maxDepth int) ([]ProcessInfo, error)
}
```

`DefaultProcessInspector` 的方法按平台编译。`pid <= 0` 时从当前进程开始，显式传入的正数深度继续有效，并统一执行硬上限和防环检查。

默认深度通过公共辅助函数按平台选择，替换 `registry.go` 中硬编码的 4。仅调整 Windows 默认值，不扩大 Linux 的扫描范围。

### 4.2 Windows 采集流程

1. 调用 `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0)`，取得一次进程快照。
2. 使用 `Process32First/Process32Next` 构建 PID 与父 PID 关系；只请求进程快照，不枚举模块、线程或内存。
3. 从起始 PID 沿父 PID 追踪，最多处理 8 个节点。
4. 对链上节点使用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid)`。
5. 用 `QueryFullProcessImageNameW` 获取实际可执行文件路径，用 `GetProcessTimes` 获取创建时间。
6. 检查父进程创建时间不晚于子进程；发现疑似 PID 复用、环或关系断裂时停止该方向追踪。
7. 释放快照及全部成功打开的进程句柄。

查询路径使用 Unicode API，缓冲区按需增长并设置上限。采集逻辑使用私有依赖接口或函数参数隔离系统调用，使访问拒绝、进程消失及读取失败能够确定性测试。

### 4.3 错误与部分结果

- 快照失败：返回错误，由诊断层记录降级原因。
- 链中进程已退出、关键元数据不可读或父子关系无法核验：停止继续追踪，不猜测后续节点。
- 已核验节点可以随错误一并返回；`InspectProcessAncestors` 应先记录告警，再处理这些已核验的部分结果，避免丢弃有效证据。
- 只有未核验的进程名、没有可用路径时，不据此生成已知宿主证据。
- 没有足够证据时保持 unknown；采集失败本身不能导致初始化选中某个工具。

### 4.4 本地宿主匹配

新增私有匹配函数，建议签名为：

```go
func matchLocalEditorProcess(info ProcessInfo) (string, bool)
```

输入必须来自当前实际祖先进程链。对系统返回的路径进行大小写和分隔符归一化，再精确匹配可执行文件名。匹配表只收录已确认特征：

- `Cursor.exe`：返回 `cursor`。这是本次在 Windows 上实际遇到漏识别的可执行文件。
- `Code.exe`、`Code - Insiders.exe`：返回 `vscode`。

`codex`、`antigravity`、`claude`、`windsurf` 尚无已确认的 Windows 可执行文件名，不进入本轮匹配表。

不得将任意目录名包含某工具名、文件名包含该词或通用 `node.exe` 视为命中；例如项目目录中的 `cursor-helper.exe` 不匹配。

该匹配入口不得接入全局 PATH 扫描。现有远程白名单保留，用于原有远程证据来源。

同一工具的多个祖先进程证据可以汇总；多个不同工具的有效宿主证据仍交给现有仲裁处理，不按白名单顺序选择。

这些证据用于宿主判断，不构成可执行文件数字签名验证、用户授权或客户端规则加载证明。

## 5. 命令集成与影响边界

### 5.1 初始化

`cmd/init.go` 只采集一次 `DetectionContext`，冲突判断后直接调用该上下文的 `EffectiveTarget()`，不再重复调用完整环境检测。

保留现有选择顺序：

1. 显式 `-t/--targets`。
2. 配置中的默认装配集合。
3. 当前识别结果，已知 Runner 优先于已知 Editor。
4. 无法识别时使用已有规则入口；仍无法确定则要求显式选择。

保留无显式目标时对冲突的阻断。VS Code 已被识别但没有可用规则档案时，沿用现有报错要求用户选择目标，不自动映射为其他工具，也不新增 VS Code 规则档案。

### 5.2 测试可注入入口

保留 `newInitCommand()` 作为生产入口；增加接受 `agent.ProcessInspector` 的内部构造入口，供测试传入模拟进程链。

`detect` 同样通过命令构造函数创建实例，测试可注入采集器，参数变量随实例隔离。生产命令仍使用默认采集器，CLI 用法不变。

现有测试不能只清理环境变量后继续读取真实开发机进程。凡断言宿主、候选或 unknown 状态的测试，都必须使用确定的模拟采集器。

### 5.3 身份与输出

- 新证据使用现有 `source=process`、`role=editor`。
- Runner 的强指纹、会话声明及优先级保持现有契约。
- `pkg/relay/relay.go` 的任务调用者仍只依据 Runner；仅发现某个 Editor 不能认领为该工具的 Runner。
- `IsAutomationEnvironmentWithProfiles` 仍依据 CI/Runner 判断，不将新 Editor 证据作为自动化执行依据。
- 保持 `detect --json` 现有字段和版本，复用证据与告警字段。
- 诊断说明展示进程名、PID、祖先级别及匹配原因，不输出完整命令行、环境变量原值或用户完整安装路径。

## 11. 指令扩写触发与诊断连续性设计

扩写漏触发和诊断跳步是规则与命令链路上的缺口，本次在 Cursor 会话中被观察到。诊断交付条件对所有宿主相同。原生事件字段只按已核对的 Cursor Hooks 编写。`--host` 用来选择适配器；本轮实现 `cursor` 这一已观察宿主，不表示其他宿主不需要扩写。

### 11.1 请求类型与流程

统一流程为：

```text
请求进入 → 意图解码 → 必要的只读诊断 → 证据与原因说明
        → 判断是否需要修改 → 修复方案 → 对应授权 → 实施 → 验证
```

“首轮”改为有明确作用域的要求：每个新任务或改变目标的请求，都应重新确认目标和动作类型；普通状态询问无需重复完整流程；纠偏应重新核对目标与已有证据；用户确认应关联已有方案，不将“执行”本身当作新故障重新诊断，也不扩大授权范围。

分支约定：

- 分析、排查、询问原因：先只读检查，再交付诊断结论。可以提出建议，不强制进入实施 Plan 或要求用户回复执行。
- 修复故障：形成可支持修改的诊断结论后，再给修复方案。
- 原因未明：列出假设、支持或反对证据以及下一项检查；此时交付的是排查计划，不是已确认根因的修复方案。
- 新功能或已经明确的改动：说明现状与预期行为差异即可，不虚构故障，也不强迫执行无关诊断。
- 明确指定文件：可以省略模型手动调用扩写 CLI，但不能以“目标明确”为由省略所需的故障原因说明。

### 11.2 触发和交付分别确认

本次接入采用“提交事件触发编译、常驻规则引导读取、可观察事件记录交付、工具执行前检查”的组合；每一环独立验证。下面的事件名来自已核对的 Cursor Hooks，是当前样本的协议，不是扩写能力的适用范围。

1. 在 beforeSubmitPrompt 事件中解析原始请求及当前工作区，调用现有编译器生成本次上下文，返回符合该事件协议的 JSON。
2. 不向 beforeSubmitPrompt 返回未受支持的改写字段，不把 stdout 中出现信封视为模型已经收到信封。
3. 对没有逐请求自动注入能力的版本，通过短小的 Always Apply 项目规则引导模型读取本次请求的上下文产物；由实际工具读取事件记录交付证据。
4. 按宿主实际能力检查工具执行前的流程状态。只完成编译、没有交付证据时，不能声称扩写链路完整；故障修复写入前还须满足诊断及用户授权要求。
5. 对工具覆盖和答复观察能力逐项实测。宿主不提供的能力标为未支持，不以文字声明代替实际拦截。

beforeSubmitPrompt 负责触发和校验，不能单独完成动态提示词改写。sessionStart 的上下文只能作为会话引导，不能代替后续每次请求的上下文更新。若改用其他官方支持的交付接口，必须先核验当前宿主版本并记录实机证据。

### 11.3 显式宿主适配模式

拟增加以下参数组合，作为本次实施的新接口，而非当前已存在的命令。`cursor` 是已核对协议的宿主值，参数形式保留给后续已核实的其他宿主：

```text
agate prompt --hook --host cursor --event beforeSubmitPrompt
agate prompt --hook --host cursor --event preToolUse
agate prompt --hook --host cursor --event postToolUse
```

适配约定：

- 未指定 `--host` 时，现有 `--hook` 和 `--json` 的行为保持不变。
- 指定宿主时，标准输入按对应原生事件解析，stdout 只输出该事件允许的 JSON；诊断信息走 stderr。
- `--host`、`--event` 必须匹配已支持组合；原生模式与普通 `--json` 同时指定时返回用法错误，防止两套输出协议混淆。
- preToolUse 处理执行前检查，postToolUse 只在观察到与本次产物对应的读取结果后更新交付记录；事件输入输出字段须依据当前官方协议逐项测试。
- 注册配置使用 Agate 二进制的明确路径，不依赖用户当前终端能否正确解析 PATH。

本地规则和 Hook 配置在用户授权安装后才启用。需要先验证当前宿主对上述事件、读取观察与工具阻断的实际支持；本次可验证的宿主是 Cursor。缺少能力时保留显式运行、显式读取的降级路径，并报告尚未达到自动链路验收条件。

### 11.5 诊断交付和进入修复方案的条件

1. 现象与预期行为：用户遇到了什么，与预期相差什么。
2. 问题位置和证据：相关文件、日志、报错或命令结果；区分实际观察与推断。
3. 因果解释：触发条件如何经过相关代码或环境导致现象。
4. 不确定项：哪些原因已确认，哪些仍是假设，以及还缺哪项检查。
5. 方案依据：拟改位置对应哪条原因，预期改变什么行为，如何验证。

原因仍未知时，不允许把修复思路表述为已证实的根因修复；排查计划可以在此阶段交付。无法获得复现环境时，明确静态分析的证据范围，不编造测试或日志。

流程状态至少区分“未诊断、待验证假设、已形成有证据的诊断结论”。只有锚定为 explicit、填完解码标题或提供一个 Plan，都不能改变诊断状态。

可以校验诊断字段、引用及步骤是否存在，并对缺失内容进行提示或在受支持工具上阻断写入；字段齐全仍不证明因果关系正确。诊断真实性依赖证据核对和适当复现，不能由模型自报完成替代。

若当前宿主没有可用的答复检查接口，应明确此处的解释性输出仍由规则约束，不能宣称所有答复均被外部强制校验。工具写入检查也不能代替对最终原因说明的验收。

### 11.6 扩写与诊断端到端验收

固定记录本次宿主版本、规则版本、事件适配版本和测试输入。当前实机会话的宿主是 Cursor。分别验收以下场景：

- [ ] 新会话中的模糊故障请求：能够观察到请求触发、编译、上下文交付，以及有证据的原因说明。
- [ ] 同一会话中另一个新问题：创建新的关联记录，不能依赖第一次请求的完成状态。
- [ ] 明确文件的故障请求：允许简化锚定过程，但修复方案前仍有必要的诊断说明。
- [ ] 纯原因分析：输出诊断结论，无不必要的实施确认。
- [ ] 原因未明：明确给出待验证假设和下一项检查，未声称根因已确认。
- [ ] 用户纠偏：旧目标对应的结论重新评估，新的 Plan 说明哪些证据或判断发生变化。
- [ ] 用户确认：只沿用被确认方案的范围，不复用其他任务的授权或重新虚构故障。
- [ ] Hook 失败、超时、无效载荷或上下文读取失败：能明确定位中断环节，不显示全部成功。
- [ ] 模型直接输出修复 Plan、缺少原因说明：答复检查能够指出缺项；若宿主版本暂不支持该检查，记录为未完成的能力，不能通过此项验收。
- [ ] 模型尝试直接修改：对已声明覆盖的原生编辑、Shell 和 MCP 路径验证流程检查；不以单一路径的拦截代替全覆盖。
- [ ] 规则分发存在旧全局来源或会话未加载新入口：能展示实际来源和差异，不能仅因文件已写入就报告生效。

交付记录应分别列出三个工作包的结果：Windows 宿主识别、扩写触发与交付、诊断连续性。只通过 `agate detect`、`agate prompt` 单元测试或解码文本格式检查，不构成整套流程通过。
